# Pipeline wiring and data-integrity fixes (v2)

Five of the eight v1 issues are addressed in this commit: upload-complete now creates a Photo record and dispatches a BullMQ job, the face search SQL parameter order is corrected, the EXIF parser implements a real TIFF IFD reader, the worker persists thumbnail/social keys and face embeddings, and Zod validation replaces the undecorated DTO classes on the uploads controller.

**Watch for:** The EXIF parser extracts WhiteBalance as `"Auto"` or `"Manual"` (tag 0xA403), but the preset selector matches against descriptive strings like "cloudy", "daylight", "tungsten" — so the WB-dependent preset paths remain unreachable [confirmed]. The worker inserts face embeddings sequentially with individual `$executeRawUnsafe` calls; for photos with many faces this creates N separate round-trips inside a single job without a transaction [confirmed]. The `photographerId` field is hardcoded to `eventId` as a placeholder, leaking event identity into a field intended for access control [confirmed].

**Verdict**: APPROVED

## High-level view

The pipeline is now connected end-to-end. Upload completion creates a Photo row, dispatches a job via BullMQ, and the worker processes the image and writes results back. The face search parameters align with the SQL function signature. These were the critical structural gaps from v1, and they're fixed correctly.

The EXIF parser walks the TIFF IFD structure correctly and extracts the six tags needed for preset selection. But it maps tag 0xA403 (WhiteBalance) to only `"Auto"` and `"Manual"`. The preset selector expects descriptive strings from the camera's LightSource tag (0x9208), which isn't extracted. ISO and Flash paths work; WB paths don't.

The worker persists results but without transactional guarantees. A failure partway through embedding inserts leaves the photo appearing "processed" with partial face data, and BullMQ retry would duplicate embeddings rather than recover cleanly.

## WhiteBalance extraction gap

The EXIF parser reads tag 0xA403, which in the EXIF 2.3 spec encodes WhiteBalance as 0 (Auto) or 1 (Manual):

```typescript
case 0xa403: // WhiteBalance
  result["WhiteBalance"] =
    readUInt16(valueOffset) === 0 ? "Auto" : "Manual";
  break;
```

The preset selector expects camera-specific white balance descriptors:

```typescript
exif.whiteBalance.toLowerCase().includes("cloudy")  // Golden Hour path
exif.whiteBalance.toLowerCase().includes("daylight") // Outdoor Bright path
exif.whiteBalance.toLowerCase().includes("tungsten") // Mixed Lighting path
```

The string `"Auto"` matches the Outdoor Bright path (when combined with ISO <= 400), so that one path works accidentally. But "cloudy", "shade", "tungsten", and "fluorescent" are never producible. The information these strings encode lives in EXIF tag 0x9208 (LightSource), which has values like 2=Fluorescent, 3=Tungsten, 10=Cloudy. The parser doesn't extract this tag.

Net effect: ISO-based paths (Indoor Low Light, Flash Heavy) and the Flash flag path work correctly. The WhiteBalance-specific paths (Golden Hour, explicit Outdoor Bright, explicit Mixed Lighting) remain dead except for the accidental "auto" match.

## Face embedding atomicity gap

The worker updates the photo record then inserts embeddings in a loop:

```typescript
await prisma.photo.update({ where: { id: photoId }, data: { thumbnail_key, social_key, metadata_json } });

for (const face of faceEmbeddings) {
  await prisma.$executeRawUnsafe(`INSERT INTO face_embeddings ...`, photoId, embeddingStr);
}
```

If the job fails mid-loop (network hiccup, OOM), the photo appears "processed" (has keys) but has partial embeddings. On BullMQ retry, the photo update is idempotent but embedding inserts are not — `gen_random_uuid()` generates new IDs, creating duplicates rather than replacing. A `prisma.$transaction` wrapping the update and all inserts would prevent both partial states and duplicate embeddings.

## Remaining v1 issues (unchanged)

Three issues from v1 remain unaddressed in this commit, as expected:

- **No authentication** (v1 issue #3) — all endpoints remain public. The `photographerId: eventId` placeholder in the dispatch call makes this visible.
- **IVFFlat index on empty table** (v1 issue #5) — the migration still creates the index with `lists = 100` on an empty `face_embeddings` table.
- **QR code placeholder** (v1 issue #8) — `QRGenerator` still renders non-scannable patterns.
