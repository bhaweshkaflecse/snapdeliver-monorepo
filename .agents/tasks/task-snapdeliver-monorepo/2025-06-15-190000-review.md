# SnapDeliver Monorepo: Greenfield Photo Delivery Platform

A full-stack SaaS for event photographers in Nepal: Tauri desktop app ingests photos from SD cards and uploads via presigned URLs to Cloudflare R2, a BullMQ worker processes images through a 6-preset pipeline with Nepal-specific color cast detection, pgvector stores face embeddings for selfie-based photo discovery, and a Next.js web app provides photographer dashboards and guest portals with native share. The architecture cleanly separates concerns: the API never touches image bytes (only dispatches jobs and generates presigned URLs), and all heavy processing lives in the isolated worker microservice.

**Watch for:** EXIF extraction is non-functional (the parser returns an empty map, meaning preset selection always falls through to "Mixed Lighting") [confirmed]. The face search SQL has parameter order reversed — `eventId` is passed where `match_threshold` is expected [confirmed]. No authentication or authorization exists on any endpoint [confirmed]. The upload-complete flow never triggers job dispatch or creates a photo database record [confirmed].

## High-level view

The API-to-worker delegation follows the correct pattern conceptually, but nothing in the API actually *calls* `JobsService.dispatchPhotoProcessing`. The upload-complete endpoint returns success without creating a database photo record or dispatching a processing job, and the worker never persists its results back to the database. The entire pipeline is disconnected at both ends.

The presigned URL flow is well-structured for the client side: the desktop client requests URLs, uploads chunks directly to R2, then confirms completion. But the confirmation endpoint does nothing beyond calling S3 `CompleteMultipartUpload` — no photo record, no job dispatch.

The offline queue handles IndexedDB persistence, network debounce, pause/resume/retry, and abort controllers correctly. `File` objects cannot survive app restarts (only metadata is persisted); the code reports this as a failure with a clear message. Sequential processing (one upload at a time) is conservative for bandwidth-constrained environments but will be slow for large batches on good connections.

The pgvector SQL function computes cosine similarity correctly (`1 - (embedding <=> query)`) with IVFFlat indexing. However, the IVFFlat index with `lists = 100` on an initially empty table cannot be used until sufficient data exists and `REINDEX` is run. More critically, the API's face search call passes parameters in the wrong order to the SQL function.

Color cast detection for Nepal party palace lighting is the only functional path into preset selection since EXIF parsing is broken. The heuristics (green > 1.3x red, magenta > 1.4x green) are reasonable for indoor event photography but could false-positive on outdoor vegetation scenes.

Security is absent at every layer: no auth middleware, no rate limiting, no input validation via the Zod schemas defined in `shared-types`, and CORS defaults to `*`.

## The pipeline integration gap

The upload flow has two halves that never connect. The desktop client calls `POST /uploads/multipart` to get presigned URLs, uploads chunks directly to R2, then calls `POST /uploads/complete`. The controller calls `UploadsService.completeMultipartUpload` which sends `CompleteMultipartUploadCommand` to S3 and returns. No photo record is created in Postgres. No job is dispatched to BullMQ. The `JobsService` exists and is correctly wired to the `photo-processing` queue, but nothing invokes it.

The worker's `ProcessingProcessor` ends with:
```typescript
// TODO: Update database with processed photo paths and face embeddings
// This will be handled by a database service in a future iteration
```

Even if a job were dispatched, the processed thumbnails, social HD images, and face embeddings would be uploaded to R2 but never recorded in the database. The face search would find nothing because `face_embeddings` is never populated.

## EXIF extraction is a no-op

`ExifService.parseExifBuffer` returns `{}` unconditionally:

```typescript
private parseExifBuffer(exifBuffer: Buffer): Record<string, string | number | undefined> {
    return {};
}
```

Since `extractExif` relies on this parsed map, it always returns `{ iso: null, whiteBalance: null, flash: false, ... }`. The preset selection logic falls through every condition and lands on "Mixed Lighting". The color analysis service is the only mechanism that can produce a non-default preset.

## Face search parameter order bug

The photos service calls the SQL function:

```typescript
const results = await prisma.$queryRawUnsafe(
  `SELECT * FROM search_wedding_photos($1::vector, $2, $3, $4)`,
  embeddingStr, eventId || null, matchThreshold, matchCount
);
```

The function signature is:
```sql
search_wedding_photos(
    query_embedding vector(512),
    match_threshold float DEFAULT 0.8,
    match_count int DEFAULT 10,
    target_event_id UUID DEFAULT NULL
)
```

Parameter `$2` receives `eventId` (string/null) but the function expects `match_threshold` (float). Parameter `$3` receives `matchThreshold` (float) but expects `match_count` (int). Parameter `$4` receives `matchCount` (int) but expects `target_event_id` (UUID). When `eventId` is null the function uses defaults for later params, which may accidentally work. When `eventId` is non-null, PostgreSQL will throw a type cast error attempting to cast a UUID string to float.

## Absent authentication

The `.env.example` includes `JWT_SECRET` and Supabase keys, suggesting auth was planned but not implemented. All endpoints are public: creating events, listing all photos, performing face searches, initiating uploads to any event's R2 prefix. `CORS_ORIGIN` defaults to `*`, meaning any origin can call the API.

## Color cast false-positive risk

The color analysis operates on a 128x128 downsample and triggers override when green exceeds 1.3x red. A naturally green scene (outdoor vegetation, green decorations filling the frame) would trigger the Color Neutralize preset, desaturating and tinting an image that doesn't need correction. For the stated use case (indoor party photography) this is acceptable, but if the product expands to outdoor events, the heuristic needs a scene classification guard.

## Shared types divergence

The `packages/shared-types` package exports Zod schemas (`PresignedUrlRequest`, `FaceSearchRequest`, `CreateEventInput`) but the NestJS API doesn't import them. Controllers define local DTO classes without `class-validator` decorators. Since `ValidationPipe` is configured with `whitelist: true`, it strips unknown properties but cannot validate types, ranges, or formats — an invalid UUID, negative file size, or missing required field passes through uncaught.

The web app's `api-client.ts` defines its own inline TypeScript interfaces rather than importing from `shared-types`, creating duplicate type definitions that can drift independently.

## QR code non-functional

`QRGenerator` renders finder patterns and deterministic dots based on a string hash — it looks like a QR code but is not scannable. The component comment acknowledges this is a placeholder. For the MVP workflow (photographer prints QR, guest scans to find photos), this means the guest discovery path is broken end-to-end.
